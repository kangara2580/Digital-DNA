# Site Structure and Editing Roadmap

작성일: 2026-05-01

목표: 현재 릴스 마켓을 “보이는 화면 중심 사이트”에서 “수정, 검수, 이력, 공개 정책이 있는 운영 가능한 마켓플레이스”로 확장한다.

## 1. 왜 수정 구조가 중요한가

이 사이트의 핵심 데이터는 영상, 이미지, 판매 정보, 구매 기록, AI 생성 결과다. 이 데이터는 한 번 만들고 끝나는 것이 아니라 계속 바뀐다.

예를 들어 판매자는 제목, 가격, 설명, 썸네일을 수정할 수 있어야 하고, Admin은 부적절한 영상의 공개 상태를 바꿀 수 있어야 한다. 그런데 변경 이력이 없으면 나중에 분쟁이 생겼을 때 “누가 언제 무엇을 바꿨는지” 알 수 없다.

따라서 앞으로의 기본 원칙은 아래와 같다.

1. 중요한 수정은 바로 DB에 저장한다.
2. 수정 전 값과 수정 후 값을 이력으로 남긴다.
3. 판매자 수정과 Admin 수정을 구분한다.
4. 공개 화면에는 승인된 데이터만 보여준다.
5. 파일 자체는 DB에 넣지 않고 Storage에 저장한다.

## 2. 현재 구조에서 보이는 리스크

| 영역 | 현재 리스크 | 개선 방향 |
| --- | --- | --- |
| 영상 데이터 | 코드 카탈로그와 DB 영상이 섞여 있음 | 장기적으로 `videos` DB 중심으로 통합 |
| 판매자 수정 | 수정 후 바로 반영됨 | 중요한 수정은 `pending` 재검수로 전환 |
| Admin 수정 | 상태 변경은 가능하지만 정보 수정 이력이 부족 | 수정 전/후 이력 기록 |
| 이미지/파일 | URL은 있으나 파일 생명주기 관리 부족 | Storage path, metadata, 정리 작업 필요 |
| 공개 노출 | 모든 흐름에서 `approved` 필터가 일관되지 않음 | 공개 API/화면에 승인 필터 적용 |
| 운영 메모 | 대상별 내부 메모가 없음 | `admin_notes` 테이블 추가 |
| CS 대응 | 회원 상세에서 구매/리뷰/신고/AI 작업을 같이 보기 어려움 | 대상 중심 상세 페이지 필요 |

## 3. 수정 권한 정책

| 수정 주체 | 가능한 수정 | 검수 필요 여부 | 기록 |
| --- | --- | --- | --- |
| 판매자 | 제목, 설명, 해시태그, 카테고리, 썸네일 | 썸네일/카테고리/설명 변경은 `pending` 권장 | `content_change_logs` |
| Admin | 제목, 설명, 가격, 상태, 카테고리, 썸네일 URL | Admin 판단으로 즉시 반영 가능 | `admin_audit_logs`, `content_change_logs` |
| 시스템 | 조회수, 판매수, AI 결과 연결 | 검수 불필요 | 필요 시 시스템 로그 |

## 4. 추천 신규 테이블

### `content_change_logs`

콘텐츠 수정 이력 테이블이다. 영상 정보가 바뀔 때 이전 값과 변경 후 값을 남긴다.

| 컬럼 | 설명 |
| --- | --- |
| `id` | 이력 ID |
| `target_type` | `video`, `profile`, `purchase` 등 |
| `target_id` | 대상 ID |
| `actor_id` | 수정한 사용자 또는 관리자 |
| `actor_type` | `seller`, `admin`, `system` |
| `change_type` | `edit`, `moderation`, `price`, `poster`, `sync` 등 |
| `before_json` | 수정 전 값 |
| `after_json` | 수정 후 값 |
| `created_at` | 생성 시각 |

### `admin_notes`

운영 메모 테이블이다. 고객에게 보이지 않는 내부 메모를 남긴다.

| 컬럼 | 설명 |
| --- | --- |
| `id` | 메모 ID |
| `target_type` | `user`, `video`, `purchase`, `report`, `generation_job` |
| `target_id` | 대상 ID |
| `body` | 메모 내용 |
| `created_by` | 작성 관리자 |
| `created_at` | 작성 시각 |

## 5. 공개 노출 정책

`videos.status`를 사이트 전체에서 일관되게 사용한다.

| 상태 | 의미 | 공개 화면 |
| --- | --- | --- |
| `approved` | 공개 승인 | 노출 |
| `pending` | 검수 대기 | 판매자/Admin만 |
| `rejected` | 반려 | 판매자/Admin만 |
| `hidden` | 숨김 | Admin만, 또는 기존 구매자 제한 접근 |

첫 적용 범위:

1. 공개 피드/카테고리/검색은 `approved`만 노출한다.
2. 판매자 마이페이지는 본인 영상 전체 상태를 본다.
3. Admin은 모든 상태를 본다.

## 6. Admin 상세 페이지 분리 계획

현재 `/admin`은 1차 콘솔이다. 데이터가 늘어나면 아래처럼 분리한다.

| 페이지 | 목적 |
| --- | --- |
| `/admin` | 전체 요약 |
| `/admin/videos` | 영상 검색, 필터, 수정, 검수 |
| `/admin/users` | 회원 상세, 메모, 제재 |
| `/admin/purchases` | 구매, 환불, 정산 |
| `/admin/reports` | 신고 처리 |
| `/admin/jobs` | AI 작업 재시도/실패 관리 |
| `/admin/audit-logs` | 관리자 기록 검색 |

## 7. 이번 개발에서 먼저 구현할 범위

| 작업 | 이유 |
| --- | --- |
| `content_change_logs` 추가 | 수정 이력 기반 |
| `admin_notes` 추가 | 운영 메모 기반 |
| Admin 영상 정보 수정 폼 | 실제 운영에서 가장 자주 필요한 수정 기능 |
| 판매자 수정 시 `pending` 전환 | 판매자가 바꾼 내용은 다시 검수 가능해야 함 |
| 수정 이력 기록 helper | Admin/판매자/시스템 변경을 같은 방식으로 기록 |
