# Admin Next Operations and UX Plan

작성일: 2026-05-01

목표: 실제 배포 후 사용자 업로드, Kling 3.0 Motion Control 생성 결과, 대량 데이터 운영까지 감당할 수 있도록 Admin과 DB 흐름을 정리한다.

## 1. 질문 답변

### Q1. 사람들이 릴스를 올리면 Admin에 들어가는가?

현재 코드 기준으로는 “DB에는 들어간다”가 맞다.

판매자 업로드 API는 `/api/sell/upload`이고, 업로드가 성공하면 `videos` 테이블에 새 row를 만든다. 따라서 Admin이 `videos` 테이블을 읽으면 새 릴스가 Admin에 보일 수 있다.

다만 지금 상태는 운영 기준으로 한 가지 부족하다.

현재 업로드 API는 새 영상을 만들 때 `status`를 명시하지 않는다. 그래서 DB 기본값인 `approved`로 들어갈 가능성이 높다. 즉, 배포하면 사용자가 올린 영상이 “검수 대기”가 아니라 “승인됨” 상태로 들어갈 수 있다.

운영 기준으로는 반드시 아래처럼 바꿔야 한다.

| 항목 | 현재 | 배포 전 목표 |
| --- | --- | --- |
| 판매자 업로드 저장 | `videos`에 저장됨 | 유지 |
| 기본 상태 | `approved` 가능성 | `pending` |
| Admin 노출 | Admin에서 조회 가능 | `/admin/videos?status=pending`에서 바로 확인 |
| 공개 노출 | approved 필터가 붙은 곳부터 제한 | 전체 공개 피드/상세까지 일관 적용 |

결론: 업로드 데이터는 Admin DB로 들어갈 준비가 되어 있지만, 배포 전에는 **새 업로드 기본 상태를 `pending`으로 바꾸는 작업**이 필요하다.

### Q2. 유저들이 Kling 3.0 Motion Control로 만든 URL도 DB에 모을 수 있는가?

가능하다. 다만 현재 흐름이 두 갈래다.

| 흐름 | 현재 저장 상태 |
| --- | --- |
| `/api/reels/generate` | `generation_jobs` DB에 저장됨 |
| `/api/kling/motion-control` 직접 호출 | 현재는 로컬 `kling_tasks_db.json`에 임시 저장 |

즉, 우리가 만든 AI 생성 작업 흐름은 이미 DB에 저장된다. 하지만 Kling Motion Control API를 직접 호출하는 라우트는 아직 운영 DB 저장 방식이 아니다.

배포 기준으로는 `/api/kling/motion-control`도 아래 정보를 DB에 저장해야 한다.

| 저장할 값 | 이유 |
| --- | --- |
| 요청한 사용자 ID | 누가 생성했는지 추적 |
| 입력 이미지 URL | 생성 원본 확인 |
| 입력 영상 URL | 어떤 릴스를 기반으로 만들었는지 확인 |
| prompt | 생성 요청 내용 확인 |
| Kling task id | Kling 결과 조회/문제 추적 |
| external task id | 내부 추적 ID |
| 상태 | queued/running/succeeded/failed |
| 결과 URL | 생성된 최종 영상 |
| 오류 메시지 | 실패 원인 확인 |

추천은 새 테이블을 만들기보다 우선 `generation_jobs`에 통합하는 것이다. 이미 AI 작업 Admin 화면이 이 테이블을 보고 있기 때문이다.

## 2. 배포 전 반드시 필요한 백엔드 작업

| 우선순위 | 작업 | 이유 |
| --- | --- | --- |
| 1 | 판매자 업로드 기본 상태 `pending` 처리 | 사용자 업로드가 자동 공개되면 위험 |
| 2 | 공개 피드 전체 `approved` 필터 적용 | 숨김/반려/검수대기 영상 노출 방지 |
| 3 | `/api/kling/motion-control` DB 저장 | Kling 결과 URL과 작업 추적 |
| 4 | Storage path 저장 | 나중에 파일 정리, 용량 관리 가능 |
| 5 | Admin 영상 상세/수정 페이지 분리 | 데이터가 많아질수록 카드 UI만으로 부족 |
| 6 | 관리자 액션 성공/실패 피드백 | 버튼 눌렀을 때 처리 결과를 운영자가 알아야 함 |

## 3. 자료가 많아질 때 필요한 Admin UI/UX

### 3.1 접고 펴는 구조

Admin은 정보가 많기 때문에 모든 것을 한 번에 펼치면 피곤하다. 기본은 접고, 필요한 것만 펼치는 방식이 좋다.

| 영역 | 기본 상태 | 이유 |
| --- | --- | --- |
| 필터 패널 | 펼침 | 운영자가 가장 먼저 검색해야 함 |
| 영상 수정 폼 | 접힘 | 카드마다 입력창이 너무 많으면 화면이 무거움 |
| 상태 변경 버튼 | 펼침 | 자주 쓰는 핵심 액션 |
| 운영 메모 | 접힘 | 필요할 때만 작성 |
| 수정 이력 | 접힘 | 조회성 정보 |
| 외부 원본 링크 | 펼침 | TikTok 원본 확인이 중요 |

### 3.2 “더보기” 구조

현재는 페이지네이션이 들어갔다. 운영자 입장에서는 두 가지 방식이 필요하다.

| 방식 | 쓰기 좋은 곳 |
| --- | --- |
| 페이지네이션 | Admin 목록, 검색 결과 |
| 더보기 | 대시보드 요약, 최근 작업 |

추천:

- `/admin` 요약 화면: 각 섹션은 5개만 보여주고 “더보기” 버튼 제공
- `/admin/videos`: 페이지네이션 유지
- `/admin/users`: 페이지네이션 유지
- `/admin/jobs`: 최신 20개 + 상태 필터
- `/admin/reports`: open/reviewing 우선 노출

### 3.3 빠른 액션 버튼

영상 카드마다 모든 버튼을 항상 펼치면 복잡하다. 아래처럼 액션을 나누는 것이 좋다.

| 액션 | UI |
| --- | --- |
| 승인 | 카드 상단 고정 버튼 |
| 숨김 | 위험 액션 영역 |
| 반려 | 사유 입력 후 버튼 |
| 정보 수정 | “수정 열기” 버튼을 눌렀을 때만 표시 |
| 메모 | “메모 열기” 버튼을 눌렀을 때만 표시 |
| 이력 | “이력 보기” 버튼 |

### 3.4 운영 큐

Admin 첫 화면에는 모든 데이터보다 “오늘 처리해야 할 것”이 먼저 보여야 한다.

추천 큐:

1. 검수 대기 영상
2. 실패한 AI 작업
3. open 신고
4. 환불/취소 요청
5. 최근 숨김 처리된 영상

## 4. 추천 다음 개발 순서

가장 실용적인 순서:

1. `/api/sell/upload` 기본 `status: pending` 적용
2. `/api/kling/motion-control`을 `generation_jobs`에 저장
3. `/admin/videos` 카드의 수정/메모 폼 접기/펼치기 UI 적용
4. `/admin` 요약 섹션에 “더보기” 링크 적용
5. `/admin/jobs` 독립 페이지 생성
6. 실패 AI 작업 재시도 버튼 추가
7. 공개 피드 전체 DB/approved 기준 통일

## 5. 다음 개발 턴 추천 범위

다음 개발에서는 아래 3개를 한 번에 처리하는 것이 가장 좋다.

| 작업 | 결과 |
| --- | --- |
| 업로드 기본 `pending` | 사용자 릴스가 Admin 검수로 들어감 |
| Kling DB 저장 | Motion Control 생성 URL/작업 ID가 Admin에 쌓임 |
| Admin 접기/펼치기 UI | 관리자가 많은 자료를 편하게 볼 수 있음 |
