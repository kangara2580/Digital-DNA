# Admin Expansion Roadmap

작성일: 2026-05-01

목표: 현재 Admin 1차 콘솔을 실제 운영 조직이 쓸 수 있는 관리 시스템으로 확장한다. 핵심은 회원정지, 권한 관리, 콘텐츠 검수, 구매/환불, 신고 처리, 정산, 감사 로그를 서로 연결하는 것이다.

## 1. 현재 상태 요약

현재 Admin은 아래 기능까지 들어와 있다.

| 영역 | 현재 상태 |
| --- | --- |
| 회원 | `profiles` 목록 조회 가능 |
| 이미지/영상 | `videos` 목록 조회, 승인/대기/반려/숨김 상태 변경 가능 |
| 구매 | `purchases` 목록 조회, paid/refunded/canceled 상태 변경 가능 |
| AI 작업 | `generation_jobs` 상태 조회 가능 |
| 신고 | `reports` 상태 변경 및 관리자 메모 가능 |
| 감사 로그 | `admin_audit_logs` 기록 조회 가능 |
| 카탈로그 동기화 | 코드 카탈로그 영상을 DB로 동기화하는 버튼 존재 |

아직 부족한 부분은 “운영 정책”이다. 지금은 데이터를 보고 일부 상태를 바꿀 수 있지만, 회원정지나 판매자 제한처럼 사이트 전체 흐름에 영향을 주는 정책은 아직 공통으로 묶여 있지 않다.

## 2. 가장 먼저 필요한 기능 목록

| 우선순위 | 기능 | 왜 필요한가 |
| --- | --- | --- |
| 1 | 회원 상태 관리 | 악성 회원, 결제 문제 회원, 신고 누적 회원을 제한해야 한다. |
| 2 | 판매자 상태 관리 | 판매자만 업로드/수정/정산 제한을 따로 걸 수 있어야 한다. |
| 3 | Admin 권한 등급 | 모든 관리자에게 환불/회원정지 권한을 주면 위험하다. |
| 4 | 운영 메모 | 회원/영상/구매/신고마다 내부 메모가 필요하다. |
| 5 | 검색/필터 | 데이터가 많아지면 최근 12개만 보는 방식은 부족하다. |
| 6 | 신고 자동 연결 | 신고가 들어오면 회원/영상 상태와 연결되어야 한다. |
| 7 | 공개 노출 정책 | `approved` 영상만 공개 화면에 보여야 한다. |
| 8 | 정산/환불 기초 | 구매 상태 변경과 판매자 정산 상태가 분리되어야 한다. |

## 3. 회원정지 설계

회원정지는 단순히 `profiles.status = suspended` 하나로 끝내면 안 된다. 정지 종류마다 막아야 하는 행동이 다르기 때문이다.

| 정지 유형 | 막는 행동 | 예시 |
| --- | --- | --- |
| `login_suspended` | 로그인 이후 서비스 이용 차단 | 계정 도용, 심각한 약관 위반 |
| `purchase_suspended` | 구매 차단 | 결제 악용, 환불 남용 |
| `seller_suspended` | 판매/업로드/수정 차단 | 저작권 침해 업로드 |
| `review_suspended` | 리뷰/댓글 차단 | 욕설, 허위 리뷰 |
| `ai_suspended` | AI 생성 차단 | 부적절한 이미지 생성 시도 |

추천 방식은 `profiles`에 단일 상태를 넣는 것보다 별도 테이블을 두는 것이다.

### 추천 신규 테이블: `user_restrictions`

| 컬럼 | 설명 |
| --- | --- |
| `id` | 제재 ID |
| `user_id` | 대상 회원 |
| `restriction_type` | `login`, `purchase`, `seller`, `review`, `ai` |
| `status` | `active`, `expired`, `revoked` |
| `reason` | 관리자 사유 |
| `starts_at` | 시작 시각 |
| `ends_at` | 종료 시각. 영구 정지는 null |
| `created_by` | 처리 관리자 |
| `revoked_by` | 해제 관리자 |
| `created_at` | 생성 시각 |
| `updated_at` | 수정 시각 |

이 구조의 장점:

- 한 회원에게 여러 제재를 동시에 걸 수 있다.
- 구매만 막고 로그인은 허용하는 식의 세밀한 운영이 가능하다.
- 기간제 정지와 영구 정지를 모두 지원한다.
- 해제 기록도 남길 수 있다.

## 4. 판매자 관리 설계

판매자는 일반 회원보다 운영 리스크가 크다. 업로드, 판매, 정산, 가격 변경 권한이 있기 때문이다.

### 추천 신규 테이블: `seller_profiles`

| 컬럼 | 설명 |
| --- | --- |
| `user_id` | 판매자 회원 ID |
| `seller_status` | `active`, `pending`, `suspended`, `banned` |
| `display_name` | 판매자명 |
| `bio` | 판매자 소개 |
| `payout_status` | `not_ready`, `ready`, `paused` |
| `risk_score` | 운영 리스크 점수 |
| `reviewed_by` | 검수 관리자 |
| `reviewed_at` | 검수 시각 |

Admin에서 필요한 액션:

- 판매자 승인
- 판매자 일시정지
- 판매자 영구차단
- 정산 보류
- 판매자 메모 작성

## 5. Admin 권한 등급 설계

지금은 `ADMIN_EMAILS`에 들어간 사람은 모두 같은 권한이다. 운영자가 늘어나면 위험하다.

### 추천 권한 단계

| 권한 | 가능한 일 |
| --- | --- |
| `viewer` | 조회만 가능 |
| `moderator` | 영상 승인/반려, 신고 처리 |
| `support` | 회원 메모, 구매 상태 조회, CS 처리 |
| `finance` | 환불/정산 상태 변경 |
| `super_admin` | 회원정지, 관리자 권한 변경, 위험 작업 전체 |

### 추천 신규 테이블: `admin_members`

| 컬럼 | 설명 |
| --- | --- |
| `user_id` | 관리자 회원 ID |
| `email` | 관리자 이메일 |
| `role` | 권한 등급 |
| `status` | `active`, `disabled` |
| `created_by` | 초대한 관리자 |
| `created_at` | 생성 시각 |

초기에는 `ADMIN_EMAILS`를 유지하되, 이후에는 `admin_members` 테이블로 이전하는 것이 좋다.

## 6. 운영 메모 설계

운영자는 회원, 영상, 구매, 신고마다 내부 메모를 남겨야 한다. 메모는 고객에게 보이지 않는 내부 기록이다.

### 추천 신규 테이블: `admin_notes`

| 컬럼 | 설명 |
| --- | --- |
| `id` | 메모 ID |
| `target_type` | `user`, `video`, `purchase`, `report`, `generation_job` |
| `target_id` | 대상 ID |
| `body` | 메모 내용 |
| `created_by` | 작성 관리자 |
| `created_at` | 작성 시각 |

활용 예시:

- 회원: “환불 요청 3회, 다음 요청 시 finance 확인 필요”
- 영상: “저작권 출처 확인 전까지 hidden 유지”
- 구매: “PG사 환불 대기”
- 신고: “동일 사용자 반복 신고로 모니터링 필요”

## 7. 검색/필터/페이지네이션

현재 Admin 데이터 조회는 최근 12개 중심이다. 운영 데이터가 늘어나면 반드시 검색과 필터가 필요하다.

| 화면 | 필요한 검색/필터 |
| --- | --- |
| 회원 | 이메일, 닉네임, 전화번호, 상태, 국가 |
| 영상 | 제목, 판매자, 상태, 카테고리, AI 여부 |
| 구매 | 구매자, 판매자, 영상 ID, 상태, 기간 |
| AI 작업 | 사용자, 상태, 실패 여부, 기간 |
| 신고 | 대상 유형, 상태, 담당 관리자 |
| 감사 로그 | 관리자, 액션, 대상, 기간 |

구현 방식:

1. `/admin`은 요약 대시보드로 유지한다.
2. `/admin/users`, `/admin/videos`, `/admin/purchases`처럼 상세 페이지를 나눈다.
3. URL query로 필터를 표현한다. 예: `/admin/videos?status=pending&q=dance`
4. 서버에서 `take`, `skip`, `where` 조건으로 페이지네이션한다.

## 8. 공개 노출 정책

현재 `videos.status`는 Admin에서 바꿀 수 있다. 다음으로 중요한 것은 실제 공개 화면에서 이 상태를 반영하는 것이다.

정책:

- `approved`: 공개 화면 노출
- `pending`: Admin만 확인 가능
- `rejected`: 판매자에게 반려 사유 표시, 공개 안 함
- `hidden`: 기존 구매자는 접근 가능할 수 있지만 신규 노출은 안 함

필요한 코드 변경:

| 영역 | 변경 |
| --- | --- |
| 공개 영상 목록 API | `status = approved` 조건 추가 |
| 상세 페이지 | hidden/rejected 접근 정책 추가 |
| 판매자 마이페이지 | 본인 영상은 pending/rejected도 볼 수 있게 처리 |
| Admin | 모든 상태 조회 가능 |

## 9. 결제/정산 확장 설계

현재 `purchases.status`는 구매 상태만 나타낸다. 하지만 실제 운영에서는 결제와 정산은 분리해야 한다.

### 추천 신규 테이블: `settlements`

| 컬럼 | 설명 |
| --- | --- |
| `id` | 정산 ID |
| `seller_id` | 판매자 |
| `purchase_id` | 구매 기록 |
| `gross_amount` | 총 결제 금액 |
| `platform_fee` | 플랫폼 수수료 |
| `net_amount` | 판매자 정산 금액 |
| `status` | `pending`, `payable`, `paid`, `held`, `canceled` |
| `paid_at` | 지급 시각 |

구매 상태와 정산 상태를 분리해야 하는 이유:

- 구매는 paid지만 정산은 held일 수 있다.
- 환불되면 정산도 canceled가 되어야 한다.
- 저작권 신고가 들어오면 정산만 보류할 수 있다.

## 10. 신고 자동화 설계

신고는 단독으로만 있으면 운영자가 놓치기 쉽다. 신고는 영상/회원/판매자와 연결되어야 한다.

추천 정책:

- 같은 영상에 신고 3건 이상: 자동 `pending_review`
- 저작권 신고: 즉시 `hidden` 추천
- 같은 회원이 신고 5건 이상 받음: 회원 리스크 표시
- 신고 처리 시 반드시 `admin_audit_logs` 기록

추가하면 좋은 컬럼:

| 위치 | 컬럼 |
| --- | --- |
| `reports` | `severity`, `category`, `resolved_at`, `resolved_by` |
| `videos` | `risk_score`, `last_reported_at` |
| `seller_profiles` | `risk_score` |

## 11. AI 생성 작업 운영 설계

AI 작업은 비용과 안전성 문제가 있어 Admin에서 관리가 필요하다.

필요 기능:

- 실패 작업 재시도
- 특정 사용자 AI 생성 제한
- 작업별 비용 추적
- 작업 입력값/결과값 확인
- 부적절 결과 신고 연결

추천 신규 컬럼:

| 테이블 | 컬럼 |
| --- | --- |
| `generation_jobs` | `cost_cents`, `model_name`, `retry_count`, `review_status` |

## 12. 추천 개발 순서

가장 안전한 순서:

1. `admin_members`, `user_restrictions`, `admin_notes` 테이블 추가
2. Admin 권한 등급 helper 추가
3. 회원정지/해제 server action 추가
4. 회원 상세 패널에 제재 상태와 메모 표시
5. 리뷰/구매/판매/AI API에서 제재 여부 확인
6. `/admin/users` 상세 페이지 분리
7. `/admin/videos` 검색/필터/페이지네이션 분리
8. 공개 영상 목록에 `approved` 필터 적용
9. 신고 자동화와 리스크 점수 추가
10. 정산 테이블과 finance 권한 추가

## 13. 1차 개발 추천 범위

다음 개발 턴에서 바로 구현하기 좋은 범위:

| 작업 | 이유 |
| --- | --- |
| `user_restrictions` 테이블 추가 | 회원정지의 핵심 기반 |
| `admin_notes` 테이블 추가 | 운영 메모 기반 |
| 회원정지/해제 버튼 | Admin이 바로 사용할 수 있는 운영 기능 |
| 리뷰 작성 API에 `review` 제재 확인 | 정지된 회원이 리뷰를 못 쓰게 함 |
| 구매 API에 `purchase` 제재 확인 | 정지된 회원이 구매를 못 하게 함 |
| AI 생성 API에 `ai` 제재 확인 | 비용/안전 리스크 차단 |

이 범위가 끝나면 Admin은 단순 조회 도구가 아니라 “회원 행동을 실제로 제한할 수 있는 운영 도구”가 된다.

## 14. 쉬운 용어 설명

| 용어 | 뜻 |
| --- | --- |
| 회원정지 | 회원의 일부 또는 전체 기능 사용을 막는 것 |
| 권한 등급 | 관리자마다 할 수 있는 일을 다르게 나누는 것 |
| 운영 메모 | 고객에게 보이지 않는 내부 기록 |
| 리스크 점수 | 신고/환불/위반 기록을 바탕으로 위험도를 숫자로 보는 것 |
| 페이지네이션 | 데이터가 많을 때 1페이지, 2페이지처럼 나눠 보는 것 |
| 정산 | 구매 금액 중 판매자에게 지급할 금액을 계산하고 지급하는 것 |
